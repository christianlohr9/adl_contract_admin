- Direct DB access via async_session (no running server)
- openpyxl for spreadsheet reading (read_only=True, data_only=True)
- extract_player_name() strips "TEAM POS" suffix from spreadsheet names
- Call service functions directly (bypass window gating)
- team_id scoping required for conference-aware checks (FT, EXT, ERFA, RFA)
- Team IDs: 129-144 = NFC, 145-160 = AFC

**Known expected discrepancies (NOT bugs — do not attempt to fix):**
- Already-actioned players: DB reflects post-action state (extended, tendered, etc.), spreadsheet is pre-action snapshot → ~20-30 players per tool
- Scoring data gaps: ~7 players where DB player ranks differ from spreadsheet TSP_RK (affects 5YO/PPE levels)
- Conference-scoped accrued seasons: DB computes league-wide, spreadsheet uses conference-scoped → affects ERFA/RFA eligibility for ~30 players
- Name encoding: ~9 players with apostrophes/dots not found in DB (D.K. Metcalf, A.J. Barner, etc.)
- Robust PR enforcement: ~40 EXT players where app enforces bylaws rule spreadsheet doesn't check
- 6 players missing from DB entirely

**Constraining decisions:**
- This phase is REPORT ONLY — do not fix discrepancies, do not modify app code
- Discrepancy-only output — don't flood with matching rows
- Enough diagnostic context per mismatch to pinpoint (player, tool, field, expected vs actual, category)

  <name>Task 1: Cross-tool eligibility sweep</name>
  <files>scripts/validate_cross_tool.py, .planning/phases/23-cross-tool-validation/23-01-VALIDATION.md</files>
  <action>
Build a one-time cross-tool validation script that sweeps all 1,549 players from TagElig26 and compares eligibility flags for all tools.

**Script structure** (follow validate_ft_eligibility.py patterns):

1. **Load spreadsheet** — Read TagElig26 tab. For each row extract:
   - Player name (col 1), Conf (col 12) for team_id derivation
   - EXT* flag (col 6): "oEXT" or "iEXT" means eligible, None means ineligible
   - FT flag (col 7): "FT" means eligible
   - RFA flag (col 8): "RFA" means eligible
   - ERFA flag (col 9): "ERFA" means eligible
   - ORFArd/5YO flag (col 10/11): presence means eligible (these are 5YO candidates)
   - Note: B/R eligibility is not in TagElig26 (all contracted players are eligible per bylaws) — skip B/R eligibility comparison

2. **Match players to DB** — Use extract_player_name() pattern. Build a name→Player lookup dict from DB. Track unmatched players.

3. **For each matched player, run all eligibility checks:**
   - `check_tag_eligibility(session, player.id, 2026, team_id)` → compare vs FT column
   - `check_extension_eligibility(session, player.id, 2026, team_id)` → compare vs EXT* column (eligible if EXT* is "oEXT" or "iEXT")
   - `check_erfa_eligibility(session, player.id, 2026, team_id)` → compare vs ERFA column
   - `check_rfa_eligibility(session, player.id, 2026, team_id)` → compare vs RFA column
   - `check_buyout_eligibility(session, player.id, 2026)` → no spreadsheet column to compare, but run for error detection
   - 5YO/PPE: Skip eligibility here (validated in PPE5YO tab in Task 2)

   Derive team_id from conference column: look up player's contract team_id from DB, or use Conf column to filter (NFC=129-144, AFC=145-160).

4. **Categorize each discrepancy** into one of:
   - `ALREADY_ACTIONED` — app says ineligible because player was re-signed/tendered/extended (reason contains "already re-signed" or "active contract")
   - `ACCRUED_SEASONS` — ERFA/RFA mismatch due to conference-scoped accrued data gap
   - `ROBUST_PR` — EXT mismatch where app enforces robust PR rule spreadsheet doesn't check
   - `NOT_FOUND` — player not matched in DB
   - `POTENTIAL_BUG` — unexplained discrepancy (flag for investigation)

5. **Output eligibility section** of validation report to .planning/phases/23-cross-tool-validation/23-01-VALIDATION.md:
   - Per-tool summary: total checked, matches, discrepancies by category
   - Discrepancy table (discrepancies ONLY): player, tool, SS says, app says, app reason, category
   - Omit all matching rows
   - Count of POTENTIAL_BUG discrepancies prominently displayed

Run the script and capture output. If POTENTIAL_BUG count > 0, investigate each one and document root cause. Do NOT fix code — only document.

IMPORTANT: Do not create the script as a reusable CLI tool. It's a one-time validation run. Inline constants are fine. The script itself is the means, the report is the deliverable.
